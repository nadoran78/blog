개발을 처음 시작했을 때는 아키텍처라고 하면

```text
Controller
↓
Service
↓
Repository
```

형태의 레이어드 아키텍처가 전부인 줄 알았다.

하지만 경력이 쌓이고 다양한 프로젝트를 접하다 보니, 아키텍처는 단순히 코드 구조가 아니라

> 어떤 문제를 해결하기 위해 어떤 트레이드오프를 선택했는가

에 더 가깝다는 생각이 들었다.

이번 글에서는 최근 백엔드 개발자들이 자주 이야기하는 대표적인 아키텍처들을 간단히 정리해보려 한다.

---

## 1. 레이어드 아키텍처 (Layered Architecture)

가장 전통적이고 널리 사용되는 구조.

```text
Controller
↓
Service
↓
Repository
↓
Database
```

### 장점

- 이해하기 쉽다.
    
- 학습 비용이 낮다.
    
- Spring Boot 기본 구조와 잘 맞는다.
    

### 단점

- 서비스가 비대해지기 쉽다.
    
- 도메인보다 기술 계층 중심으로 사고하게 된다.
    
- 규모가 커질수록 변경 영향 범위가 커진다.
    

### 추천 상황

- 소규모 프로젝트
    
- 스타트업 초기 서비스
    
- 빠른 개발이 필요한 경우
    

---

## 2. 헥사고날 아키텍처 (Hexagonal Architecture)

내가 가장 많이 경험한 구조.

Ports & Adapters Architecture라고도 부른다.

```text
도메인
↑
Port
↑
Adapter
```

핵심 아이디어는

> 비즈니스 로직이 외부 기술(DB, API, Framework)에 의존하지 않도록 하자

이다.

### 장점

- 테스트가 쉽다.
    
- 도메인 중심 설계가 가능하다.
    
- 기술 교체에 유연하다.
    

### 단점

- 초기 구조가 복잡하다.
    
- 작은 프로젝트에는 과한 경우가 많다.
    
- Adapter와 Port가 남발될 수 있다.
    

### 추천 상황

- 비즈니스 로직이 중요한 서비스
    
- 장기 운영 예정 프로젝트
    
- 테스트 자동화 비중이 높은 조직
    

---

## 3. 클린 아키텍처 (Clean Architecture)

헥사고날과 상당히 비슷한 철학을 가진 구조.

```text
Framework
↓
Adapter
↓
Use Case
↓
Domain
```

의존성은 항상 안쪽을 향한다.

### 장점

- 도메인 순수성 유지
    
- 테스트 용이
    
- 외부 기술 교체 가능
    

### 단점

- 구현 복잡도 증가
    
- 학습 비용 존재
    
- 작은 프로젝트에는 과함
    

### 추천 상황

- 복잡한 도메인
    
- 금융
    
- 결제
    
- ERP
    

---

## 4. Modular Monolith

요즘 개인적으로 가장 현실적이라고 생각하는 구조.

```text
하나의 애플리케이션

├─ order
├─ payment
├─ coupon
├─ member
└─ lecture
```

배포는 하나지만 내부는 강하게 모듈화한다.

### 장점

- MSA보다 단순
    
- 모듈 경계 유지 가능
    
- 운영 부담 적음
    

### 단점

- 모듈 경계 관리 필요
    
- 방치하면 다시 거대한 모놀리스가 됨
    

### 추천 상황

- 대부분의 SaaS
    
- 스타트업
    
- 중소 규모 서비스
    

솔직히 현재 시점에서는

> MSA를 고민하기 전에 Modular Monolith를 먼저 고민하는 것이 더 현실적이라고 생각한다.

---

## 5. Vertical Slice Architecture

요즘 많이 언급되는 구조.

기능 단위로 코드를 나눈다.

```text
coupon/

  issue/

  use/

  expire/
```

### 장점

- 기능 변경 범위가 명확
    
- 관련 코드가 한 곳에 모임
    
- 유지보수 쉬움
    

### 단점

- 공통 코드 관리 필요
    
- 패키지 구조가 낯설 수 있음
    

### 추천 상황

- 기능 중심 조직
    
- 빠른 기능 개발
    

---

## 6. Event-Driven Architecture

이벤트를 중심으로 시스템을 설계하는 방식.

```text
주문 생성됨

↓

결제

↓

쿠폰 차감

↓

알림 발송
```

### 장점

- 느슨한 결합
    
- 확장성 좋음
    
- 비동기 처리에 강함
    

### 단점

- 추적 어려움
    
- 디버깅 난이도 상승
    
- 이벤트 순서 관리 필요
    

### 추천 상황

- 알림
    
- 결제
    
- 정산
    
- 대규모 트래픽
    

---

## 7. CQRS

읽기와 쓰기를 분리하는 구조.

```text
Command
=
쓰기

Query
=
조회
```

### 장점

- 조회 성능 최적화
    
- 복잡한 대시보드 구현 쉬움
    

### 단점

- 구조 복잡
    
- 데이터 동기화 문제
    

### 추천 상황

- 통계 시스템
    
- 관리자 대시보드
    
- 분석 플랫폼
    

---

## 8. Saga Pattern

분산 트랜잭션 처리 패턴.

예를 들어

```text
주문 생성

↓

쿠폰 차감

↓

결제 승인

↓

수강권 발급
```

중간에 실패하면 이전 작업을 보상 처리한다.

### 장점

- 분산 시스템에 적합
    
- 강력한 확장성
    

### 단점

- 구현 난이도 높음
    
- 운영 난이도 높음
    

### 추천 상황

- 마이크로서비스
    
- 결제 시스템
    

---

## 9. Event Sourcing

상태가 아니라 이벤트를 저장한다.

```text
쿠폰 발급

쿠폰 사용

쿠폰 취소

쿠폰 만료
```

이벤트가 진실(Source of Truth)이 된다.

### 장점

- 완벽한 이력 추적
    
- 감사 로그 강력
    

### 단점

- 매우 복잡
    
- 러닝커브 높음
    

### 추천 상황

- 금융
    
- 회계
    
- 정산
    
- 포인트
    

---

## 10. 마이크로서비스 아키텍처 (MSA)

한때 업계의 정답처럼 여겨졌던 구조.

```text
Order Service

Payment Service

Coupon Service

Member Service
```

### 장점

- 독립 배포
    
- 독립 스케일링
    
- 팀별 소유권
    

### 단점

- 운영 복잡도 증가
    
- 분산 트랜잭션
    
- 장애 추적 어려움
    

### 추천 상황

- 대규모 조직
    
- 수십 개 이상의 팀
    

---

## 그래서 무엇을 공부해야 할까?

개인적으로는

```text
Layered
↓
Hexagonal
↓
Modular Monolith
↓
Event Driven
↓
CQRS
```

순서가 가장 현실적이라고 생각한다.

많은 개발자들이 MSA를 공부하려고 하지만 실제로는

> MSA를 잘하기 위해 먼저 Modular Monolith를 잘해야 한다.

는 이야기가 점점 많아지고 있다.

---

## 결국 아키텍처의 목적은 같다

마틴 파울러는 아키텍처를

> "중요한 것들에 대한 결정"

이라고 표현했다.

결국 어떤 아키텍처를 선택하더라도 목표는 같다.

```text
변경하기 쉽고

이해하기 쉽고

확장하기 쉬운 시스템
```

을 만드는 것.

그리고 좋은 아키텍처는 거창한 다이어그램보다

> 새로운 기능을 추가할 때 얼마나 덜 고통스러운가

로 평가받는다고 생각한다.
