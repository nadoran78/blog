
하네스 엔지니어링이라는 말을 듣기는 많이 들었지만, 정확히 무엇을 의미하는지는 잘 몰랐다.

처음에는 `AGENTS.md`를 잘 작성하거나 프롬프트 규칙을 정리하는 정도라고 생각했다. 하지만 OpenAI가 Codex로 실제 제품을 만든 사례를 읽어보니, 하네스 엔지니어링은 그보다 훨씬 넓은 개념이었다.

> **AI 에이전트가 코드를 안정적으로 작성하고, 스스로 검증하고, 실패하면 다시 수정할 수 있도록 개발 환경 전체를 설계하는 일**

이라고 이해하는 것이 가장 가까워 보인다.

OpenAI 팀은 약 5개월 동안 사람이 직접 코드를 작성하지 않고 Codex를 통해 내부 제품을 만들었다. 애플리케이션 코드뿐 아니라 테스트, CI, 문서, 내부 도구와 관측 가능성 설정까지 Codex가 작성했다고 한다.

중요한 점은 단순히 Codex에게 많은 코드를 생성시킨 것이 아니다.

사람은 다음과 같은 환경을 만드는 데 집중했다.

- 에이전트가 읽을 수 있는 문서 구조
    
- 기계적으로 검증되는 아키텍처 규칙
    
- 자동 테스트와 리뷰 루프
    
- UI·로그·메트릭을 에이전트가 직접 확인할 수 있는 환경
    
- 반복적으로 발생하는 문제를 자동으로 정리하는 작업
    

즉, 사람의 역할이 코드 작성에서 **에이전트가 제대로 일할 수 있는 시스템 설계**로 이동한 것이다.

## AGENTS.md 하나로는 부족하다

처음 하네스 엔지니어링을 접하면 `AGENTS.md`에 모든 규칙을 적으면 될 것처럼 느껴진다.

하지만 OpenAI 팀도 하나의 거대한 `AGENTS.md`를 사용하는 방식은 실패했다고 설명한다.

문서가 너무 길어지면 에이전트는 중요한 제약을 놓치고, 오래된 규칙과 현재 규칙을 구분하지 못한다. 모든 지침이 중요하다고 적혀 있으면 실제로는 아무것도 중요하지 않은 상태가 된다.

그래서 `AGENTS.md`를 백과사전이 아니라 **목차와 지도**로 사용했다.

```text
AGENTS.md
ARCHITECTURE.md

docs/
├── design-docs/
├── exec-plans/
│   ├── active/
│   └── completed/
├── product-specs/
├── references/
├── DESIGN.md
├── RELIABILITY.md
└── SECURITY.md
```

에이전트는 짧은 `AGENTS.md`에서 출발해 현재 작업에 필요한 문서만 찾아 읽는다.

이 구조가 중요한 이유는 컨텍스트가 제한되어 있기 때문이다. 처음부터 모든 정보를 넣는 대신, 필요한 정보를 단계적으로 찾을 수 있도록 만들어야 한다.

## 문서보다 강한 것은 기계적인 제약이다

문서에 아키텍처 규칙을 적어두는 것만으로는 코드베이스를 일관되게 유지할 수 없다.

에이전트는 기존 코드에서 발견한 패턴을 반복한다. 코드베이스에 잘못된 구조가 하나 들어오면 그 구조가 계속 복제될 수도 있다.

OpenAI 팀은 이를 막기 위해 아키텍처 경계를 린터와 구조적 테스트로 강제했다.

예를 들어 각 도메인의 코드가 다음 방향으로만 의존하도록 제한했다.

```text
Types
  ↓
Config
  ↓
Repository
  ↓
Service
  ↓
Runtime
  ↓
UI
```

허용되지 않은 방향으로 의존하면 문서상의 권고로 끝나는 것이 아니라 빌드나 검증 단계에서 실패한다.

이 부분을 보고 하네스 엔지니어링의 차이를 조금 더 분명하게 이해했다.

```text
문서에 규칙을 작성한다
→ 규칙을 알려주는 것

린터와 테스트로 규칙을 검사한다
→ 규칙을 지키게 만드는 것
```

하네스는 후자에 더 가깝다.

## 에이전트가 스스로 확인할 수 있어야 한다

AI가 코드를 작성하더라도 결과를 확인할 방법이 없다면 사람의 검토 부담은 크게 줄어들지 않는다.

그래서 OpenAI 팀은 Codex가 직접 애플리케이션을 실행하고 확인할 수 있는 환경을 만들었다.

Codex는 작업별로 격리된 애플리케이션을 실행하고 다음 작업을 수행할 수 있었다.

1. 버그를 재현한다.
    
2. UI 상태와 로그를 확인한다.
    
3. 코드를 수정한다.
    
4. 애플리케이션을 다시 실행한다.
    
5. 수정 결과를 검증한다.
    
6. Pull Request를 생성한다.
    
7. 리뷰와 빌드 실패에 대응한다.
    

UI뿐 아니라 로그, 메트릭, 추적 정보도 에이전트가 조회할 수 있도록 제공했다.

결국 좋은 하네스는 AI에게 단순히 코드 편집 권한만 주는 것이 아니다.

> **코드를 작성하고, 실행하고, 관찰하고, 검증하고, 다시 수정하는 전체 루프를 제공한다.**

## 하네스 엔지니어링을 순차적으로 적용하는 방법

OpenAI 사례는 상당히 큰 규모의 실험이다. 개인 프로젝트에서 처음부터 동일한 환경을 만들려고 하면 하네스 구축 자체가 목적이 될 수 있다.

따라서 아래와 같이 작은 단계부터 순차적으로 적용해보는 것이 좋을 것 같다.

### 1단계: 프로젝트의 지도 만들기

먼저 짧은 `AGENTS.md`를 만든다.

여기에 모든 개발 규칙을 넣기보다 에이전트가 어디서 필요한 정보를 찾을 수 있는지 기록한다.

```markdown
# AGENTS.md

## 프로젝트 개요
- 이 프로젝트가 해결하는 문제
- 주요 사용자
- 핵심 기술 스택

## 작업 전 확인
- 아키텍처: ARCHITECTURE.md
- 테스트 기준: docs/TESTING.md
- 현재 계획: docs/plans/active/
- 주요 결정: docs/decisions/
```

첫 단계의 목표는 완벽한 문서를 만드는 것이 아니다.

> **프로젝트의 중요한 지식이 사람의 머릿속이나 채팅에만 남지 않게 만드는 것**

이다.

### 2단계: 반복해서 말하는 규칙을 문서로 옮기기

AI에게 매번 반복해서 설명하는 내용이 있다면 별도 문서로 만든다.

예를 들면 다음과 같다.

```text
ARCHITECTURE.md
TESTING.md
DOMAIN.md
CONVENTIONS.md
```

다만 문서는 가능한 한 짧게 유지하고, 실제 코드와 맞지 않는 규칙은 바로 수정하거나 삭제해야 한다.

### 3단계: 문서 규칙을 자동 검증으로 옮기기

문서에만 있는 규칙 중 기계적으로 확인할 수 있는 것을 찾는다.

예를 들면 다음과 같다.

- 테스트 통과 여부
    
- 코드 포맷
    
- 순환 의존성
    
- 허용되지 않은 레이어 의존
    
- 파일 크기
    
- 패키지 명명 규칙
    
- 특정 모듈 간 직접 참조 금지
    

그리고 이를 린터, 테스트, 스크립트나 CI로 옮긴다.

```text
문서에만 존재하는 규칙
→ 사람이 기억해야 함

CI에서 검사하는 규칙
→ 에이전트도 반드시 따라야 함
```

하네스가 강해지는 지점은 규칙이 설명에서 자동 검증으로 바뀔 때다.

### 4단계: 작은 실행·검증 루프 만들기

AI가 코드를 수정한 뒤 최소한 다음 과정은 스스로 수행하게 한다.

```text
코드 수정
→ 포맷 검사
→ 단위 테스트
→ 통합 테스트
→ 실패 원인 분석
→ 수정
→ 다시 테스트
```

처음부터 복잡한 멀티 에이전트 시스템을 만들 필요는 없다.

`./gradlew test`나 하나의 검증 스크립트부터 시작해도 충분하다.

### 5단계: 작업 계획을 저장소에 남기기

복잡한 작업은 에이전트가 한 번에 끝내도록 요청하지 않고 실행 계획을 먼저 작성하게 한다.

```text
docs/plans/active/
└── implement-payment-retry.md
```

계획에는 다음 내용을 기록한다.

- 해결할 문제
    
- 변경 대상
    
- 구현 순서
    
- 검증 방법
    
- 결정한 내용
    
- 현재 진행 상태
    
- 남은 위험
    

작업이 끝나면 `completed/`로 옮긴다.

이렇게 하면 세션이 끊기거나 모델이 바뀌어도 진행 상황을 다시 복구하기 쉽다.

### 6단계: 에이전트가 직접 관찰할 수 있게 만들기

그다음에는 에이전트가 결과를 직접 확인할 수 있도록 범위를 넓힌다.

백엔드 프로젝트라면 다음 정도부터 시작할 수 있다.

- 애플리케이션 실행 스크립트
    
- API 호출용 스크립트
    
- 테스트 데이터 생성
    
- 로그 조회
    
- 데이터베이스 상태 확인
    
- 주요 시나리오 재현 명령
    

예를 들어 다음 명령 하나로 핵심 시나리오를 검증할 수 있게 만드는 것이다.

```bash
./scripts/verify-order-flow.sh
```

AI에게 긴 설명을 제공하는 것보다, 신뢰할 수 있는 검증 명령 하나를 제공하는 편이 더 효과적일 수 있다.

### 7단계: 실패를 하네스 개선으로 연결하기

AI가 실수했을 때 단순히 현재 코드만 고치고 끝내지 않는다.

다음 질문을 추가로 던진다.

> 같은 실수를 다시 하지 않으려면 문서, 테스트, 린터, 스크립트 중 무엇을 추가해야 하는가?

그 결과를 다음 중 하나로 남긴다.

```text
잘못된 이해
→ 문서 수정

재현 가능한 버그
→ 회귀 테스트 추가

반복되는 구조 위반
→ 린터 또는 구조 테스트 추가

검증하기 어려운 동작
→ 실행·관측 도구 추가
```

이 과정이 반복되면 프로젝트는 점차 AI가 일하기 좋은 환경으로 변한다.

### 8단계: 정기적인 가비지 컬렉션 추가하기

규칙과 문서가 늘어나면 오래된 내용도 함께 쌓인다.

따라서 정기적으로 다음을 검사해야 한다.

- 실제 코드와 맞지 않는 문서
    
- 중복된 규칙
    
- 사용되지 않는 유틸리티
    
- 동일한 역할을 하는 여러 구현
    
- 완료되지 않은 오래된 계획
    
- 반복해서 등장하는 기술 부채
    

처음에는 사람이 월 1회 확인해도 된다. 이후 반복 가능한 항목부터 에이전트 작업이나 자동 검사로 옮기면 된다.

## 내가 먼저 적용해볼 최소 하네스

개인 프로젝트에서 처음 적용한다면 다음 정도로 시작하면 될 것 같다.

```text
AGENTS.md
ARCHITECTURE.md

docs/
├── plans/
│   ├── active/
│   └── completed/
├── decisions/
└── TESTING.md

scripts/
└── verify.sh
```

그리고 작업 흐름을 아래처럼 고정한다.

```text
1. AGENTS.md와 관련 문서를 읽는다.
2. 구현 전 계획을 작성한다.
3. 사람이 계획을 검토한다.
4. 작은 단위로 구현한다.
5. verify.sh를 실행한다.
6. 실패하면 수정하고 다시 검증한다.
7. 사람이 코드와 결과를 검토한다.
8. 재발 방지책을 문서·테스트·규칙에 반영한다.
```

이 정도만 적용해도 단순히 프롬프트를 잘 쓰는 것과는 꽤 다른 개발 방식이 된다.

## 마무리

하네스 엔지니어링은 특별한 도구나 프레임워크의 이름이 아니었다.

`AGENTS.md`, 문서, 테스트, 린터, CI, 샌드박스, 관측 가능성, 작업 계획처럼 기존에도 사용하던 요소들을 **AI 에이전트가 안정적으로 일할 수 있도록 연결하는 방식**에 가깝다.

핵심은 AI에게 더 자세히 지시하는 데 있지 않다.

> **AI가 올바르게 작업했는지 스스로 확인할 수 있고, 실수하면 다시 고치며, 같은 실수를 반복하지 않도록 프로젝트를 개선하는 구조를 만드는 것**

이 하네스 엔지니어링의 실제 모습으로 보인다.

나도 처음부터 거대한 자동화 시스템을 만들기보다,

```text
프로젝트 지도
→ 지식 문서화
→ 자동 검증
→ 실행·관측 루프
→ 실패의 재발 방지
```

순서로 하나씩 적용해봐야겠다.
